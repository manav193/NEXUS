# Identity & Data Governance\n\nNEXUS provides a control boundary for authenticated, user-scoped data access. It does not prescribe a specific database, object-storage provider, authentication vendor, or UI.\n\n## Identity\n\nAn identity has a stable NEXUS identity ID plus an external provider and subject. Application authentication remains outside the core; the authenticated identity is passed into NEXUS for authorization.\n\n## Resource ownership\n\nEvery protected resource has an owner ID and storage key. Cross-user access is denied unless an explicit non-owner policy is supplied.\n\nRecommended logical namespace: `users/<owner-id>/<resource-type>/<resource-id>`. This does not require physical folders.\n\n## Data classification\n\nResources are classified as PUBLIC, INTERNAL, PERSONAL, SENSITIVE, or RESTRICTED. Higher classifications require explicit policy.\n\n## Consent\n\nConsent is scoped by identity, purpose, and optionally resource type. Consent can expire or be revoked. Purpose-specific consent must not be treated as blanket consent for unrelated uses.\n\n## Deletion and export\n\nDelete and export are explicit operations and are denied by default. Production implementations should provide authenticated and auditable workflows for both.\n\n## Storage boundary\n\nNEXUS should not use GitHub as user-data storage. Photos, private chats, documents, and recordings belong in dedicated application storage. NIMO-KNOWLEDGE can store authorized derived knowledge and references.\n\n## Production requirements\n\nUse durable storage, encryption at rest and in transit, authenticated identities, tenant-aware database constraints, least-privilege service credentials, audit retention controls, backup deletion policies, and appropriate privacy/legal review.
